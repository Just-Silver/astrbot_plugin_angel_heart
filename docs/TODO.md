### 提示词页每次渲染都重建 PromptModuleLoader（日志噪音，非 bug）

**现象**

`PromptModuleLoader.__init__` 每次构造都会读取 7 个文件并打 DEBUG，共 8 行：

```
[DBUG] core.prompt_module_loader:46: 成功加载模块: identity.md   ×7
[DBUG] core.prompt_module_loader:81: 组装提示词模板，使用 instruction_prompts.md，总长度: 3756
```

**实测频率（此前描述「刷屏」是夸大的，已更正）**

| 操作 | 触发次数 |
| --- | --- |
| 打开提示词页 | 1 次（`onMounted`） |
| 切换到提示词 tab 只看不操作 | 0 次 |
| 在页内改字 | 每次 1 次（`watch` 监听 draft） |
| 群消息巡检 | **0 次（已实测确认）** |

所以它不是持续刷屏，而是「每次进入/改字占 8 行」。

**真正会重建模板的三处**

| 位置 | 触发时机 |
| --- | --- |
| `core/llm_analyzer.py:76` `__init__` | 插件启动一次 |
| `core/llm_analyzer.py:107` `reload_config` | 保存配置一次 |
| `web_api/prompt_preview.py` `_render_secretary()` | 每次预览渲染一次 ← 只有这处是多余的 |

**已修（d652ff9）**

预览改为懒加载单例 `_get_preview_loader()`，同一进程只读一次文件。
属于降低日志噪音的优化，不影响功能。

**剩余观察**

AstrBot 控制台环形缓冲 `CACHED_SIZE = 500`（`astrbot/core/log.py:33`，硬编码不可配）。
高频改字预览仍会占用缓冲，若以后影响排查，再把预览的模块加载日志降级为不打印。

### 纯图片 / 文字依附图片的消息永远得不到处理

**现象**

群里只发一张图，秘书看不到内容，判 `no_reply`，事件被 `stop_event` 终止，主脑（支持图片）永远不会被唤起。

「图片 + 文字」分两种，结果相反：

| 消息 | 秘书看到 | 结果 |
| --- | --- | --- |
| `这个报错怎么解` + 截图 | `这个报错怎么解` | ✅ 文字自足，能判，链路通 |
| `好亮啊` + 照片 | `好亮啊` | ❌ 文字依附图片，判不出，链断 |
| 纯图片 | 空字符串 | ❌ 必然不回 |

**成因（已查证，非 bug）**

- 秘书调用是 `provider.text_chat(prompt=prompt)`，签名上就没有图片位置（见 [`llm_request_ownership.md`](architecture/llm_request_ownership.md)）。
- `convert_content_to_string` 只取 `type == "text"`，`image_url` 被静默丢弃，秘书**连「这条消息带图」都不知道**。
- `process_image_captions_if_needed` 是上游弃用的遗留死代码，不走它。

**候选方案**

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| A. 纯图直通 | `body_text` 为空且有图 → 跳过秘书，直接放行 | **必回**。表情包也会被回一句，群里很吵 |
| B. 给秘书 `[图片]` 标记 | 文本化时保留占位，配规则「看到 `[图片]` 但判断不了内容就放行」 | 保留「可以不回」；但要改提示词，影响刚验收过的接话率 |
| C. 按文字长度分档 | 图 + 少于 N 字就直通 | 判据粗糙，「好亮啊」3 字跳、「这个报错怎么解」8 字不跳 |

**约束（必须先确认）**

事件一旦放行，AstrBot 核心必然产生一条回复，不存在「放行但主脑自己决定不回」。所以方案 A 的副作用是确定的，不是概率性的。

**倾向**

B。它是唯一保留「可以不回」的选项。但需先做实验确认加 `[图片]` 标记不会破坏已有的关注范围判断。
